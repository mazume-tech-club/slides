DOMと仮想DOMを
体系的に理解する

ブラウザが木をどう扱い、なぜ仮想DOMが生まれ、いま何を選べるか。

矢印キーで進む。スライド内のボタンはデモで、ページは進まない。

00導入

今日のあと、説明できること

  • 01DOMはHTMLの文字列ではなく、ブラウザが持つ文書のオブジェクト木である。
  • 02画面更新はスタイル、レイアウト、ペイント、合成に分かれ、読み書きの順でコストが変わる。
  • 03仮想DOMの仕事は「速いDOM操作」ではなく、宣言したUIと実DOMの差を埋めることである。
  • 04ほかに、コンパイル（Svelte）と細かい購読（Solid、Vue Vapor）がある。

01DOMとは

ブラウザは文字列を描かない

  1. バイト列を文字へ復号する
  2. 開始タグ、テキスト、終了タグへ切る
  3. トークンからノードを積み、木にする
  4. document がその木の入口になる

HTMLパーサは、整形式でなくても木を修復しながら作る。XMLのように失敗させて終わらせるパーサではない。

defer も async もなく、type=module でもない script は、その位置でパースを止めて実行される。

画面向けのCSSは、通常、CSSOMが揃うまで最初の描画を待つ。あとから来た規則で、塗った結果を捨てたくないため。

小さな文書と、その木

01DOMとは

ノードの種類

種類例よく触るAPI
Elementdiv、pquerySelector、classList
TextこんにちはtextContent、nodeValue
Commentコメント通常は触らない
DocumentdocumentcreateElement
DocumentFragment一時的な親溜めてから一度に挿入
DocumentType<!DOCTYPE html>ほぼ触らない

属性は子ノードではない。Attr はノードだが、childNodes には並ばない。 querySelectorAll の NodeList は静的。getElementsByTagName の HTMLCollection はライブで、後からのDOM変更が結果に映る。

01DOMとは

探す、作る、つなぐ


const list = document.querySelector("#notes");
const item = document.createElement("li");
item.textContent = "DOMノードを足す";
list.appendChild(item);
  • querySelector は最初の1件。無ければ null。
  • textContent は文字列のまま入れる。innerHTML はマークアップとして解釈するので、信頼できない文字列には使わない。
  • appendChild は、すでに木にあるノードを渡すと移動になる。
  • DocumentFragment に溜めて親へ足すと、断片自体は残らず、子だけが移る。

01DOMとは

ボタンでノードを足す

  • querySelector
  • appendChild

追加は createElement と appendChild。行のクリックで打ち消し線。

リスナーは ul に1つだけ。後から足した行にも効く。次のスライドがその仕組み。

最初の2行はHTMLに書いてある。空文字は足さない。

01DOMとは

イベントは木を伝わる

capture

窓の外から、登録した親を通って対象へ降りる。第3引数 true。

target

実際にイベントが起きたノード。

bubble

すべてが上がるわけではない。focus と scroll はバブリングしない。focusin はする。

フレームのたびに全部は走らない。変更の種類によって、途中の段だけが再実行される。

02パイプライン

レンダーツリーに入るもの

箱を作る

  • 通常の要素
  • visibility: hidden。見えないが、場所は取る
  • opacity: 0。場所を取り、透明として合成できる

箱を作らない

  • display: none
  • head の meta や title
  • script

「レンダーツリー」は教材用の対応関係。Blink のレイアウトツリーなどはもっと細かい。教えるときの骨格としてはこれで足りる。

02パイプライン

どこで仕事が起きるか

Layout

箱の幅、高さ、位置。幅や文字量の変更がきっかけになりやすい。文書の広い範囲を再計算しがち。

Paint

文字、色、影、画像をレイヤに描く。塗る面積と効果が効く。

Composite

transform と opacity は、多くの場合レイアウトとペイントを飛ばしてここで済む。例外はある。

どれが支配的かはページによる。この資料にベンチマークは置かない。見るなら DevTools の Performance とレイヤ。

02パイプライン

レイアウトスラッシング


for (const el of rows) {
  const width = el.offsetWidth;
  el.style.width = width + 8 + "px";
}

幾何を読むAPIは、レイアウトが汚れていればその場で計算してから値を返す。ループで「書いて、読む」を繰り返すと、その計算が何度も走る。

これをレイアウトスラッシングと呼ぶ。読みの例は offsetWidth と getBoundingClientRect()。完全な一覧ではない。

02パイプライン

読み終えてから、書く


const widths = rows.map((el) => el.offsetWidth);
for (let i = 0; i < rows.length; i++) {
  rows[i].style.width = widths[i] + 8 + "px";
}

フレームの先頭では、前回のレイアウト結果をまだ読める。汚す前に読み、書きはまとめる。すでに汚したあとに読む必要があるなら、次のフレームへ分ける。

03素のDOM

手順を、全部書く


function render(state) {
  if (state.status === "loading") {
    root.textContent = "読み込み中";
    return;
  }
  const ul = document.createElement("ul");
  for (const name of state.names) {
    const li = document.createElement("li");
    li.textContent = name;
    ul.appendChild(li);
  }
  root.replaceChildren(ul);
}
  • 分岐のたびに、DOMへの手順が要る。
  • 前回のノードを残すか捨てるかも、自分で決める。
  • この関数は毎回リストを作り直す。差分はまだ無い。
  • 小さな画面なら、これで足りる。

03素のDOM

状態と画面が、二箇所にある

配列だけ更新した

names から B を消した。対応する li の削除を書き忘れた。画面には B が残る。

DOMだけ更新した

入力欄の文字列は要素が持っている。変数は古いまま。次の保存は、画面に無い値を送る。

バグの見た目は毎回違う。共通の原因は、正とされる状態が二箇所にあること。

03素のDOM

UIは、状態の関数


function view(state) {
  return h("ul", {}, state.names.map((name) =>
    h("li", {}, name)
  ));
}

書くのは「今の状態なら、木はこう」という値。DOMへの手順は、次の段が引き受ける。

仮想DOMはこの式の実装の一つであって、式そのものではない。

04仮想DOM

実ノードの前に、ただのオブジェクト


const vnode = {
  tag: "p",
  props: { class: "lead" },
  children: [
    { tag: "#text", props: {}, children: [], text: "こんにちは" },
  ],
};

h("p", { class: "lead" }, "こんにちは");

プレーンなオブジェクトなので、ブラウザのノードではない。比較も複製も、普通の値として書ける。比較そのものにもCPUは使う。

JSXの <p class="lead"> は、ビルドするとこの種の関数呼び出しになる。JSXは記法であり、DOMでも仮想DOMでもない。

04仮想DOM

宣言して、比べて、反映する

1. view(state)

今の状態から、新しい仮想木を作る。

2. diff

前回の仮想木と歩き、どこが違うかを決める。再調整（reconciliation）とも呼ぶ。

3. patch

決めた分だけ、実DOMを更新する。

初回は比較相手が無い。仮想木を、そのまま実ノードに展開する。

04仮想DOM

同じ型なら残し、違う型なら捨てる

タグが同じ

ノードは残す。変わった属性とテキストだけ書き、子へ降りる。

タグが違う

その部分木は捨てて作り直す。フォーカスや、入力途中の文字列はDOMが持っていたものなので消える。

これは最小の編集手順の証明ではない。実装が採用した規則。Reactの文書は、型が違う要素は別の木を生む、と仮定している。

04仮想DOM

keyは、リスト項目の同一性


items.map((item) =>
  h("li", { key: item.id }, item.name)
);
  • 無いと、多くの実装は同じ位置の子どうしを対応づける。
  • 挿入や並べ替えで、別の項目が同じDOMノードを使う。
  • チェック、入力途中の文字、内部状態が隣の項目へずれる。
  • 兄弟の中で安定して一意ならよい。添字は、並びが変わらないときだけ安全。
  • Reactでは、別の親へ移った子は key では追わない。

04仮想DOM

最適差分は重い。なので探さない

木の編集距離

ある木を別の木へ変える最小手順は、一般的なアルゴリズムだと O(n³)。n はノード数。

Reactのヒューリスティック

最小手順は探さない。O(n) で、次の2つを仮定する。

  1. 型が違う要素は、別の木を生む。
  2. 開発者が key で、安定な子を示せる。

現行のReactはこの処理を Fiber で小さな仕事に分けて進める。仮定の説明は legacy の reconciliation 文書にあり、そこには古いクラスコンポーネントのライフサイクルも出てくる。リストと key の現行の説明は react.dev。

05ミニ実装

hは、仮想ノードを返す


function h(tag, props, ...children) {
  return {
    tag,
    props: props ?? {},
    children: children.flat().map(normalize),
    el: null,
  };
}

function normalize(child) {
  if (child != null && typeof child === "object") return child;
  return {
    tag: "#text",
    props: {},
    children: [],
    text: String(child),
    el: null,
  };
}

このあとの実装とデモは、同じ関数を使っている。本番のReact要素とは別物で、説明のための最小実装。

05ミニ実装

初回は、木を実ノードにする


function createDom(vnode) {
  if (vnode.tag === "#text") {
    vnode.el = document.createTextNode(vnode.text ?? "");
    return vnode.el;
  }
  const el = document.createElement(vnode.tag);
  setProps(el, {}, vnode.props);
  for (const child of vnode.children) el.appendChild(createDom(child));
  vnode.el = el;
  return el;
}

function setProps(el, prev, next) {
  const names = new Set([...Object.keys(prev), ...Object.keys(next)]);
  for (const name of names) {
    if (name === "key") continue;
    if (prev[name] === next[name]) continue;
    const value = next[name];
    if (value == null || value === false) el.removeAttribute(name);
    else el.setAttribute(name, value === true ? "" : String(value));
  }
}

key は同一性の印なので、属性としては出さない。

05ミニ実装

同じ位置なら、ノードを残す


function patch(parent, prev, next, mode) {
  if (!prev) return parent.appendChild(createDom(next));
  if (!next) return prev.el.remove();
  const sameKey = mode === "key" ? prev.props.key === next.props.key : true;
  if (prev.tag !== next.tag || !sameKey) {
    parent.replaceChild(createDom(next), prev.el);
    return;
  }
  if (next.tag === "#text") {
    if (prev.text !== next.text) prev.el.nodeValue = next.text;
    next.el = prev.el;
    return;
  }
  next.el = prev.el;
  setProps(next.el, prev.props, next.props);
  patchChildren(next.el, prev.children, next.children, mode);
}

mode が "index" のとき、sameKey は常に真。key が違っても、同じ位置のノードを使い回す。

05ミニ実装

keyがある子は、引いてから動かす


function patchChildren(parent, prevs, nexts, mode) {
  if (mode !== "key") {
    const length = Math.max(prevs.length, nexts.length);
    for (let i = 0; i < length; i++) patch(parent, prevs[i], nexts[i], mode);
    return;
  }
  const prevByKey = new Map();
  for (const node of prevs) {
    if (node.props.key != null) prevByKey.set(node.props.key, node);
  }
  const used = new Set();
  nexts.forEach((next, index) => {
    const key = next.props.key;
    const prev = key != null ? prevByKey.get(key) : prevs[index];
    if (prev) used.add(prev);
    patch(parent, prev, next, mode);
  });
  for (const prev of prevs) {
    if (!used.has(prev) && prev.el) prev.el.remove();
  }
  for (const next of nexts) parent.appendChild(next.el);
}

同じ親の子は、全部 key を持つか、まったく持たないか、を仮定している。最後の appendChild は、既存ノードを新しい順へ移動する。

05ミニ実装

チェックは、仮想DOMの外に残る

データの順:

位置で対応

keyで対応

ラベルと番号は両方ともデータどおりに更新される。チェックだけがDOMノードの状態。左は位置に残り、右は項目についてくる。両方にチェックしてから操作する。

06誤解

「仮想DOMは速い」は、比較相手が要る

手で必要箇所だけ

変更箇所だけを命令的に触るコードより、差分計算の分だけ仕事が増えることがある。

毎回捨てて作る

親を空にして作り直すコードよりは、壊さなくてよいノードを残しやすい。

その後のレイアウト

速さを決めるのは差分の有無だけではない。再計算の範囲、key、ブラウザが受けるレイアウトの量も効く。

仮想DOMは、速さを保証するデータ構造ではない。React Compiler はメモ化で再レンダーを減らすもので、再調整をやめる機能ではない。

06誤解

価値は、宣言的な更新

  • 01画面を、状態の関数として書ける。
  • 02更新漏れの責任を、差分の規則へ移せる。
  • 03同じ宣言を、DOM以外へ渡せる。Reactの要素木は React Native ではネイティブのビューに写される。
  • 04「仮想DOM」という語はブラウザ実装を指すことが多い。要素木という考え方は、DOM専用ではない。

07ほかの選択肢

Svelteは、コンパイルする

コンポーネントを、変わった箇所をDOMへ書く JavaScript に変換する。実行時に仮想DOMの木を差分する仕組みは持たない。

Svelte 5 の runes は、コンパイラへの記法である。$state は関数ではなく、コンパイラが認識する印。

リストの同一性は、each ブロックのキー式で示す。


{#each items as item (item.id)}
  <li>{item.name}</li>
{/each}

07ほかの選択肢

Solidは、購読した箇所だけ更新する

  • コンポーネント関数は、初回にDOMへ出すとき一度だけ実行される。状態が変わっても、関数全体は再実行されない。
  • シグナルを読んだ箇所だけが購読者になる。値が変わると、そのテキストや属性の更新が走る。
  • For は要素の値の同一性でノードを対応づける。同じ値が別の位置に来れば、ノードを作り直さず移動できる。

木全体を仮想DOMとして差分する方式ではない。

07ほかの選択肢

Vueは仮想DOMが既定。Vaporは別モード

Vue 3 安定版

テンプレートをレンダラ関数にし、仮想DOMでマウントし、依存が変わったら新しい木とパッチする。コンパイラは静的な部分に印を付け、実行時に見る範囲を狭める。

Vapor（3.6 RC）

オプトインの別コンパイル。SFCを直接のDOM操作にする。すべてVaporのアプリは createVaporApp() で、仮想DOMランタイムを読み込まない、とリリースノートにある。

2026年10月時点で 3.6 はリリース候補。Vapor は安定版の既定ではない。VNode や公開インスタンスに依存する機能は対象外、ともノートにある。速度の比較値は載せていない。

07ほかの選択肢

何を差分し、何を書くか

方式 実行時に木を差分するか 更新が追うもの 主な記述
素のDOM しない 自分で選んだノード 手順
React する（Fiber） コンポーネントの要素木 UIを返す関数
Vue 3 安定版 する。範囲はコンパイラが狭める 仮想ノード テンプレート
Vue Vapor 純粋な構成ではしない コンパイルされたDOM操作 テンプレート。3.6 RC、オプトイン
Svelte しない コンパイルされたDOM操作 テンプレート
Solid しない シグナルの購読先 JSXとシグナル

この表は速さの順位ではない。

07ほかの選択肢

選び方

  • 01状態遷移が多い画面は、宣言的なモデルの方が更新漏れを減らしやすい。
  • 02ランタイムを小さく、更新箇所を購読で決めたいなら Svelte、Solid。Vapor はリリース候補として試す。
  • 03どれを選んでも、レイアウトスラッシングや巨大リストの設計は残る。
  • 04公開ベンチマークの数字では選ばない。この資料も載せていない。

08まとめ

説明できるかの確認

  • 01DOMはパースされた文書の木で、APIで読み書きする。
  • 02描画はスタイル、レイアウト、ペイント、合成に分かれ、読み書きの混在がレイアウトを同期的に走らせる。
  • 03仮想DOMは、UIの宣言をオブジェクトの木にし、前回との差分をDOMへ反映する手段である。
  • 04key は速さのスイッチではなく、リスト項目の同一性である。
  • 05速いから仮想DOM、ではない。Svelte、Solid、Vue Vapor は別の実装である。
